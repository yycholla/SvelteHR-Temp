# Implementation Plan: Production Docker Deployment with CI/CD and Caddy

**Input**: Feature specification from `/specs/040-it-is-now/spec.md`

## Summary

This feature transforms the existing development Docker setup into a production-ready deployment system with full CI/CD automation. The primary requirement is to enable one-command deployment of the SvelteHR application stack (PostgreSQL, Redis, Rust GraphQL, SvelteKit frontend, Caddy reverse proxy) to production servers with automated builds, tests, and deployments via GitHub Actions pushing to GitLab Container Registry.

**Technical Approach**:
- Modernize existing `docker-compose.prod.yml` to use current stack (Rust GraphQL instead of Hasura)
- Replace Nginx with Caddy for automatic SSL via Let's Encrypt with localhost fallback
- Implement GitHub Actions workflow with GitLab Container Registry integration
- Add automated pg_dump backups before migrations
- Configure dual-mode operation (localhost testing → production domain)
- No hard resource limits initially (monitor-first approach)

## Implementation Notes

### Critical Decision Points

1. **GitLab Container Registry Choice** (Clarification Q1)
   - Free private registry included with GitLab
   - No separate Docker Hub subscription needed
   - Built-in authentication via CI/CD tokens

2. **GitHub Actions Only** (Clarification Q3)
   - Leverage existing GitHub familiarity
   - Push to GitLab registry from GitHub Actions
   - Simpler than maintaining dual CI/CD configurations

3. **Localhost-First Deployment** (Clarification Q5)
   - `DOMAIN=localhost` → self-signed certificates (immediate testing)
   - `DOMAIN=hr.example.com` → Let's Encrypt certificates (production)
   - No Caddyfile editing required (environment variable substitution)

4. **Monitor-Then-Limit Approach** (Clarification Q4)
   - No hard resource limits in initial deployment
   - Establish baseline with `docker stats` monitoring
   - Add limits later based on actual usage patterns
   - Commented examples in docker-compose.prod.yml

5. **Automated Backup Strategy** (Clarification Q2)
   - pg_dump before every migration in CI/CD pipeline
   - Local storage with timestamp naming
   - 7-day retention with automatic cleanup
   - Manual restoration procedure documented

### Risk Mitigation

**Deployment Risks**:
- Migration failure → Automated backup enables quick restoration
- Registry unavailable → Deployment fails gracefully, current version continues running
- Let's Encrypt rate limits → Localhost mode for testing, staging server option
- Disk space exhaustion → Log rotation, backup cleanup, image pruning

**Security Hardening**:
- Non-root users in all containers
- HTTPS-only access (HTTP → HTTPS redirect)
- SSH key-based deployment (no passwords)
- Secrets via environment variables (never committed)
- CORS policies restricting allowed origins

**Operational Readiness**:
- Health checks on all services (verify before deployment proceeds)
- Automatic restart policies (service crashes don't require manual intervention)
- Rolling updates (zero downtime deployments)
- Comprehensive logging (stdout/stderr for Docker log collection)
- Rollback procedure (change image tags, redeploy in <5 minutes)
